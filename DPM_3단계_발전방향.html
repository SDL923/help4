3단계 발전 방향

무엇을 볼지 누가 정하느냐: 사람 → 코드 → LLM

1단계 · 기존 방식

사람이 직접 찾아봄

Airflow UI · Grafana를 오가며 확인
  • 매일 UI에서 발행 상태 확인
  • 오류 시 로그를 직접 읽고 원인 판단
  • 메모리·CPU는 Grafana에서 따로 확인
  • 발행 보고 직접 작성
사람: 감시·진단·조치·보고 전부
운영 대시보드
2단계 · 대시보드 + 알림

대시보드가 모아서 알려줌

Airflow·Prometheus API로 자동 수집 · 규칙 기반
  • 통합 화면: 실행 상태와 리소스를 한 화면에서
  • 자동 보고: 매일 메신저·메일 발송
  • 오류 알림: 실패·재시도 즉시 통보
  • 오류 원인 분류: 규칙으로 분류하고 근거 로그·리소스를 함께 표시
사람: 판단·조치
3단계 · 에이전트

에이전트가 조사·제안·조치

이벤트 발생 → LLM이 tool을 골라 반복 조사
  • 상시 감시, 필요할 때 리소스 조회
  • 필요한 정보를 스스로 더 찾아 원인 분석
  • 조치 제안 → 승인 → 실행 → 결과 보고
  • 질문에 답변: "이번 주 OO제품 발행 왜 오래 걸려?"
사람: 승인·감독
대시보드의 API 호출·가공 코드 재사용 · tool로 감쌈 에이전트가 쓰는 tool

3단계 에이전트 구조도

파이썬 서비스 1개가 상시 대기하다가, 일이 생길 때만 LLM을 호출한다

코드 (규칙대로 동작) LLM 판단 승인 필요 저장 외부 시스템
DAG 수정 없음 · 폴링으로 감시, 콜백 없음 LLM은 이벤트 때만 · 평소엔 대기 실행은 승인 후에만 · 조회 tool은 읽기 전용

3단계 에이전트 동작 흐름
